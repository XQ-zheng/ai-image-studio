# AI 图片生成站 v1 设计文档

- 日期：2026-10-07
- 状态：设计已通过评审，等待用户复核本文档后进入实现计划
- 流程：Superpowers brainstorming 到 writing-plans

## 1. 背景与目标

用户不再是输入一句裸提示词。用户通过勾选图片类型、比例、风格、场景、留白要求，
再填写自己的主体和补充要求，系统把这些结构化选择组装成一段专业的 GPTImage 提示词，
然后调用 GPTImage API 出图。

v1 要跑通一条完整闭环：注册、拿到赠送积分、出图、回看历史、积分耗尽、
看到升级入口，并且站点真正部署上线可访问。

成功标准：

- 新用户注册后立即可用，账户里有 5 积分
- 每成功生成一张图扣 1 积分，失败的生成不扣分
- 用户可以回看历史记录，并看到当时使用的提示词和参数
- 积分不足时给出明确的升级提示，且不阻断后续充值功能的接入
- 站点部署上线，有一个可访问的 URL

## 2. 范围

### 2.1 v1 包含

- 首页
- 生图页（结构化选项、主体输入、补充要求）
- 注册与登录（邮箱加密码）
- 生成历史
- 积分系统（注册送 5 分，每张图 1 分）
- 积分不足时的升级提示弹窗
- 中英双语切换

### 2.2 v1 明确不做

- 真实支付（只保留升级入口，不接任何支付 SDK）
- 邮件发送（不发验证邮件，不发通知邮件）
- 运营后台
- 复杂 SEO
- 图片编辑
- 上传参考图
- 多模型切换
- 批量生成

## 3. 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | Next.js App Router（TypeScript） | 单仓全栈，前后端同一套类型，Vercel 原生支持 |
| 部署 | Vercel | 与 Next.js 一致，Cron 与函数配置开箱可用 |
| 数据库 | Supabase Postgres | 自带行级安全，事务函数可以直接写在库里 |
| 鉴权 | Supabase Auth，邮箱加密码 | 不依赖任何邮件服务 |
| 图片存储 | Supabase Storage | 与数据库同一项目，权限模型统一 |
| 样式 | Tailwind CSS 加 shadcn/ui 组件 | 与 Next.js 生态一致，组件可控 |
| 图标 | lucide-react | 统一的图标来源 |
| 国际化 | 自建类型化字典加 cookie | 只有两个语言，引入重型 i18n 框架不划算 |

## 4. 架构与目录结构

没有任何独立后端服务。所有服务端逻辑都在 Next.js Route Handler 里，
数据库的原子操作下沉到 Postgres 函数。

```
app/
  [locale]/
    page.tsx                 首页
    studio/page.tsx          生图页
    history/page.tsx         生成历史
    login/page.tsx           登录与注册
  api/
    generate/route.ts        生图编排入口
    cron/reconcile/route.ts  对账任务
components/
  studio/                    选项面板、预览区、升级弹窗
  ui/                        shadcn/ui 基础组件
lib/
  prompt/                    提示词组装（纯函数）与选项字典
  credits/                   积分记账（只调 Postgres 函数）
  openai/                    GPTImage 调用封装
  storage/                   Supabase Storage 上传
  i18n/                      中英文字典与语言读取
  supabase/                  客户端与服务端 Supabase 实例
supabase/
  migrations/                建表、函数、触发器、行级安全策略
docs/superpowers/specs/      设计文档
```

分层原则：`lib/prompt` 是纯函数，不碰网络也不碰数据库；
`lib/openai` 与 `lib/storage` 各自只负责一件事；
`app/api/generate` 只做编排，不实现业务细节。

## 5. 数据模型

### 5.1 profiles

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid，主键 | 引用 auth.users(id) |
| credits | integer，默认 0 | 当前积分余额，由 handle_new_user 在注册时置为 5 |
| created_at | timestamptz | 创建时间 |

### 5.2 credit_ledger

每次积分变动写一条流水，保证余额可追溯。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid，主键 | |
| user_id | uuid | 引用 profiles(id) |
| delta | integer | 正数为增加，负数为扣减 |
| reason | text | signup_bonus / generation / refund |
| generation_id | uuid，可空 | 关联的生成记录 |
| created_at | timestamptz | 创建时间 |

### 5.3 generations

每次生成一条记录，保存当时的全部输入，便于历史页复盘。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid，主键 | |
| user_id | uuid | 引用 profiles(id) |
| status | text | processing / succeeded / failed |
| prompt | text | 最终送给模型的完整提示词 |
| options | jsonb | 用户勾选的全部选项 |
| subject | text | 用户填写的主体 |
| notes | text | 用户的补充要求 |
| size | text | 实际请求的尺寸 |
| quality | text | 实际请求的画质 |
| storage_path | text，可空 | 成功后的图片路径 |
| error | text，可空 | 失败原因 |
| created_at | timestamptz | 创建时间 |
| updated_at | timestamptz | 更新时间 |

### 5.4 数据库函数

| 函数 | 作用 |
| --- | --- |
| handle_new_user | 由 auth.users 插入触发器调用，建 profile、把余额置为 5，并写入一条 +5 流水 |
| start_generation | 在一个事务里检查余额、扣 1 分、插入 processing 记录并写流水，余额不足时返回空 |
| refund_credit | 生成失败时退回 1 分，写入退款流水 |

扣分与建记录必须在同一个事务里完成，不要拆成两步。分开执行时，中途失败会留下
「扣了分但没有记录」的状态，而对账任务是靠扫描 `generations` 找问题的，扫不到它。
扣分本身用带条件的 UPDATE 实现，不要先查再写，先查再写在并发点击下会把余额扣成负数。

### 5.5 行级安全

用户只能读自己的 `profiles`、`credit_ledger`、`generations`。
写操作一律通过服务端使用 service role 进行，客户端不持有写权限。

## 6. 积分规则

- 注册成功：加 5（signup_bonus）
- 生成开始：减 1（generation），先预留
- 生成失败、超时、上传失败：加 1（refund）
- 生成成功：不额外动作，预留即最终扣费
- 每次生成消耗固定 1 积分，与本版画质档位无关

这套「先预留、失败退回」的记账方式在接入真实支付时可以原样复用。

## 7. 生图链路

采用同步生成加对账兜底。一次 `/api/generate` 请求的顺序：

1. 校验登录状态，取到 user_id
2. 组装提示词（调用 `lib/prompt`）
3. 调 `start_generation`，在一个事务里扣 1 分并插入 status=processing 的记录，余额不足则返回 402
4. 调 GPTImage API
5. 把返回的图片上传到 Supabase Storage
6. 更新记录为 succeeded，写入 storage_path
7. 返回图片地址给前端

任何一步失败：调 `refund_credit` 退回积分，把记录标记为 failed 并写入错误原因。

图片字节不经过函数响应体。函数只返回 Storage 地址，避免把几 MB 的
base64 数据塞进响应。

### 7.1 时长风险

Vercel 的函数运行时长有上限，而 GPTImage 出图需要几十秒。应对方式：

- v1 把画质档位固定在中等，不开放高档
- 设置 `maxDuration`，尽量贴近所选套餐的上限
- 前端提交后立即进入生成中状态，避免重复提交

### 7.2 对账任务

`/api/cron/reconcile` 由 Vercel Cron 每 5 分钟调用一次，用 `CRON_SECRET` 校验来源。
它扫描 created_at 早于 3 分钟且仍为 processing 的记录，逐条退款并标记失败。

这个任务兜住的是「函数被时长上限杀掉、退款代码没机会执行」这种情况。
有了它，用户可能丢一次结果，但积分不会被吞。

## 8. 提示词组装

第一版采用确定性模板，不调用任何大模型润色。这是已确认的设计决定。

组装顺序固定为：画面类型、主体、风格、场景、构图与留白、
画质与比例参数、补充要求。

每个选项在字典里同时带中文标签和英文片段。组装时用英文片段拼接，
用户填写的主体与补充要求原样进入模板。

这样做的收益：零额外成本、零额外延迟、同样的选择产出完全一致的提示词、
逻辑可以被单测覆盖、出问题时能精确复盘当时送了什么。

已知取舍：中文主体直接进入提示词时，模型对中文的理解不如英文。
如果后续发现出图质量受此影响，可以在这层前面加一个可选的润色步骤，
用便宜的小模型先把中文主体翻译并规范化为英文。该步骤不在 v1 范围内。

## 9. 选项字典与比例约束

选项字典存放在 `lib/prompt/catalog.ts`，每一类给出若干条目，
每条包含稳定 id、中文标签、英文标签、英文片段。

| 选项组 | 条目（v1 初始集） |
| --- | --- |
| 图片类型 | 照片写实 / 插画 / 3D 渲染 / 扁平矢量 / 水彩 |
| 比例 | 方图 1:1 / 横图 3:2 / 竖图 2:3 |
| 风格 | 简约现代 / 商务专业 / 温暖治愈 / 科技感 / 复古胶片 |
| 场景 | 纯色背景 / 室内 / 自然环境 / 城市街景 / 抽象空间 |
| 留白 | 无留白满构图 / 四周均匀留白 / 顶部留白留标题位 / 大面积负空间 |

### 9.1 比例的现实约束

GPTImage 原生支持的尺寸是三档：1024x1024（1:1）、1536x1024（3:2）、1024x1536（2:3）。
16:9 与 9:16 不在支持范围内。

因此 v1 的比例选项就是这三档，界面上如实标注为方图、横图、竖图，
不提供无法兑现的选项。实现前需要再核对一次最新参数列表，
确认是否已经支持更多尺寸。

## 10. 页面与交互

### 10.1 首页

承担产品说明与入口，不放营销长文。首屏给出真实生成的作品示例，
以及进入生图页的主按钮。示例图使用图像生成能力产出真实图片放置。

### 10.2 生图页

全站重心。左侧是选项面板（图片类型、比例、风格、场景、留白），
中间是主体输入与补充要求，右侧是结果预览区。

- 选项组使用分段控件与色板，不使用一长串下拉框
- 结果预览区在生成中显示进度状态，成功后显示图片与下载按钮
- 底部显示当前积分余额
- 提交中禁用提交按钮，避免重复扣分

### 10.3 历史页

图片网格布局。点击某条记录打开详情，展示大图、当时的完整提示词与全部参数。

### 10.4 登录页

邮箱加密码。注册成功后直接进入已登录状态，不做邮箱验证流程。
Supabase 项目初始化时必须关闭 Confirm email，否则注册流程会被邮件验证卡住。

### 10.5 升级入口

积分不足时点击生成，弹出升级提示，说明当前积分与所需积分。
弹窗内展示占位套餐与「即将开放」说明，不出现任何假的支付流程。
顶部导航也保留一个固定的升级入口。

## 11. 双语

中文与英文两个语言环境，默认中文。语言选择存在 cookie 中，
通过路由段 `[locale]` 决定文案。字典存放在 `lib/i18n/`，
键名带类型约束，缺少译文在编译期就能发现。语言切换放在顶部导航。

## 12. 错误处理与对账

| 情况 | 处理 |
| --- | --- |
| 未登录 | 跳转登录页 |
| 积分不足 | 返回 402，前端弹出升级提示 |
| 重复提交 | 前端禁用按钮；服务端检查该用户是否已有 3 分钟内仍为 processing 的记录，有则直接返回该记录，不重复扣分 |
| 模型调用失败 | 退款，记录标记 failed，前端提示可重试 |
| 模型调用超时 | 同失败处理，另有对账任务兜底 |
| 图片上传失败 | 退款，记录标记 failed |
| 读历史失败 | 页面显示空状态与重试 |

## 13. 安全

- OpenAI API Key 只存在于服务端环境变量，任何情况下不下发到浏览器
- `/api/generate` 必须校验登录态，并且只使用当前会话的 user_id
- 服务端不信任前端传来的积分、尺寸、画质等字段，这些值在服务端根据选项 id 重新解析
- `/api/cron/reconcile` 用 `CRON_SECRET` 校验，防止被外部随意调用
- 单用户加基础频率限制，避免单个账号把额度打满
- Storage 桶使用随机 uuid 路径，避免图片被顺序猜中

## 14. 验证方式

手动验证清单，覆盖主流程与关键异常：

1. 新注册账号，确认积分为 5，且 credit_ledger 里有一条 signup_bonus
2. 连续生成 5 张，确认每次都扣 1 分，余额依次递减到 0
3. 第 6 次生成时弹出升级提示，且没有产生扣分记录
4. 人为让模型调用失败，确认积分退回且记录为 failed
5. 历史页能看到全部记录，点开能看到当时的完整提示词与参数
6. 切换中英文，确认页面文案随之变化且状态不丢失

自动化测试只覆盖 `lib/prompt/` 的组装逻辑，因为它是纯函数且是产品核心。
更宽的测试套件不在 v1 范围内。

## 15. 部署与环境变量

部署路径：Vercel 关联代码仓库，Supabase 建项目并跑迁移脚本。

| 环境变量 | 用途 |
| --- | --- |
| OPENAI_API_KEY | 服务端调用 GPTImage |
| NEXT_PUBLIC_SUPABASE_URL | Supabase 项目地址 |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | 浏览器端只读访问 |
| SUPABASE_SERVICE_ROLE_KEY | 服务端写操作，仅服务端可见 |
| CRON_SECRET | 对账接口来源校验 |

Vercel Cron 配置指向 `/api/cron/reconcile`，频率为每 5 分钟一次。

## 16. 风险与待确认

1. **GPTImage 参数未核对。** 本文档中关于尺寸与响应格式的描述来自已有知识，
   因为官方文档站当前从开发环境返回 403。进入实现前需要重新核对一次，
   尤其是支持的尺寸列表与返回字段。
2. **函数时长。** 中档画质通常能在上限内完成，但不是百分之百。
   对账任务保证积分安全，但用户可能看到一次失败提示。
3. **中文主体的出图质量。** 若实际效果不理想，需要评估是否加润色层。
4. **成本控制。** 每个新账号送 5 分等于送出 5 次模型调用，
   上线前需要评估是否要加更严格的频率限制。
